# SecureChat Protocol Specification (v1) – DRAFT

> **Single source of truth.** Code in `crypto-core`, `protocol`, `server` and `client` must match this
> file. Any change to a field, order or label must be done in a PR that updates this file and is
> reviewed by all three members.
>
> Status: **DRAFT – review together on day 1**, then remove this line.

Notation: `||` = concatenation, `enc[a, b, …]` = length-prefixed encoding (§0),
`HKDF(ikm, salt, info, L)` = HKDF-SHA256 (RFC 5869), `HMAC(k, m)` = HMAC-SHA256.

---

## 0. Encoding (owner: B)

- Every field is encoded as `uint32_be(len(field)) || field`. Fields are concatenated in a fixed order.
- Strings are UTF-8. Integers (PN, N) are encoded as 4-byte big-endian values and then length-prefixed like any other field.
- The decoder rejects truncated input and trailing bytes.
- On the wire (REST / WebSocket) all binary values are **base64** strings inside JSON. Conversion happens only in `client/src/ws` and `server`, never inside `crypto-core`.

## 1. REST API (owner: A)

| Method | Path                                 | Auth          | Purpose                                         |
| ------ | ------------------------------------ | ------------- | ----------------------------------------------- |
| POST   | `/api/register`                      | –             | Create account (unique username)                |
| POST   | `/api/login`                         | – (rate-limited) | Start session, set httpOnly cookie           |
| POST   | `/api/logout`                        | session       | Delete session row, clear cookie                |
| GET    | `/api/me`                            | session       | Current user                                    |
| GET    | `/api/users`                         | session       | List users + online status                      |
| PUT    | `/api/keys/identity`                 | session       | Publish own Ed25519 public key                  |
| GET    | `/api/keys/identity/:username`       | session       | Fetch peer public key (untrusted until verified) |
| POST   | `/api/conversations`                 | session       | Create/get conversation with a user             |
| GET    | `/api/conversations/:id/messages`    | session + member | Encrypted records                            |

Types: `packages/protocol/src/api.ts`. The sender is always derived from the session.

## 2. WebSocket messages (owner: A)

Endpoint `/ws`, authenticated by the session cookie. Message types: `packages/protocol/src/ws.ts`.
The server relays a message only if the authenticated user is a member of `conversationId`, and it
sets `from` itself.

## 3. Identity keys and fingerprints (owner: B)

- Ed25519 key pair generated by the client after login; the private key lives only in memory.
- Fingerprint = `SHA-256(identityPublicKey)`, shown as hex in groups of 4 (e.g. `1a2b 3c4d …`).
- A peer is **verified** only after the user presses *Verify* after comparing fingerprints out of band.
- If the server returns a different key for a verified peer during an active conversation:
  stop the conversation, show a warning, require re-verification.

## 4. Handshake (owner: B)

### 4.1 Messages

1. **I → R** `handshake_init`: version, algorithm ids, sessionId (16 random bytes), initiatorId, responderId, `EK_I`, `nonce_I` (32 bytes)
2. **R → I** `handshake_response`: `EK_R`, `nonce_R`, `sig_R`, `conf_R`
3. **I → R** `handshake_finish`: `sig_I`, `conf_I`

### 4.2 Transcript (fixed order, initiator before responder)

| #   | Field                                   |
| --- | --------------------------------------- |
| 1   | protocol version (`SecureChat-v1`)      |
| 2–6 | algorithm ids: Ed25519, X25519, HKDF-SHA256, HMAC-SHA256, AES-256-GCM |
| 7   | sessionId                               |
| 8   | initiatorId                             |
| 9   | responderId                             |
| 10  | `IK_I` (initiator identity public key)  |
| 11  | `IK_R` (responder identity public key)  |
| 12  | `EK_I` (initiator ephemeral public key) |
| 13  | `EK_R` (responder ephemeral public key) |
| 14  | `nonce_I`                               |
| 15  | `nonce_R`                               |

`transcript = enc[fields 1..15]`, `th = SHA-256(transcript)`

### 4.3 Signatures, key derivation, confirmation

- `sig_R = Ed25519.sign(IK_R_priv, enc["SecureChat-v1-Responder", transcript])`, same for I with the initiator label.
- `dh = X25519(EK_own_priv, EK_peer)`; reject all-zero output / invalid keys.
- `rootKey    = HKDF(ikm=dh, salt=th, info="SecureChat-v1-RootKey", 32)`
- `confirmKey = HKDF(ikm=dh, salt=th, info="SecureChat-v1-ConfirmKey", 32)`
- `conf_R = HMAC(confirmKey, enc[th, "SecureChat-v1-Confirm-Responder"])`, same for I.
- Comparisons use constant-time equality.

### 4.4 State rules

- One active attempt per conversation, identified by sessionId. Messages for other sessionIds, duplicates and out-of-sequence messages are rejected.
- Initiator: established after verifying msg 2 and sending msg 3. Responder: after verifying msg 3.
- Delete `dh`, `confirmKey`, initiator's `EK_I` private key and nonces after use. Responder keeps `EK_R` as its first ratchet key pair.

## 5. Double Ratchet (owner: C)

Reference: Signal Double Ratchet spec §3 (classical, no header encryption, no skipped keys).

- `KDF_RK(rk, dhOut)`: `HKDF(ikm=dhOut, salt=rk, info="SecureChat-v1-Ratchet", 64)` → new `rk` (32) || `ck` (32)
- `KDF_CK(ck)`: `mk = HMAC(ck, 0x01)`, `ck' = HMAC(ck, 0x02)`
- Initialization:
  - Responder: `DHs = EK_R key pair`, `RK = rootKey`, waits for the first message.
  - Initiator: `DHs = new X25519 key pair`, `DHr = EK_R`, `(RK, CKs) = KDF_RK(rootKey, DH(DHs, DHr))`, sends first.
- Acceptance rule (no out-of-order support):
  - same ratchet key as current `DHr` → accept only `N == Nr`
  - new ratchet key → accept only `N == 0` and `PN == Nr` (then DH ratchet step)
  - anything else (old key, gap, repeat) → reject
- Decrypt on a **copy** of the state; replace the real state only after AES-GCM succeeds.
- Delete used `mk`, old chain keys and replaced `DHs` private keys.

## 6. Message packet (owner: C)

- Header fields: version, conversationId, sessionId, senderId, receiverId, ratchetPublicKey, PN, N.
- `AD = enc[version, conversationId, sessionId, senderId, receiverId, ratchetPublicKey, PN, N]`
- `(aesKey 32B, nonce 12B) = HKDF(ikm=mk, salt=0x00*32, info="SecureChat-v1-MessageKey", 44)`
- `ciphertext = AES-256-GCM(aesKey, nonce, plaintext, AD)` (16-byte tag appended)
- Nonce uniqueness: every `mk` is used for exactly one message, so each (key, nonce) pair is used once.
- On any failure: drop the packet, show a verification-failure warning, keep the state unchanged.
